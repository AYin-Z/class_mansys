# 对话助手架构（2026-09-12）

> 目的：说清楚"哪些已经对了、哪些还缺、按什么顺序补"。所有结论都有实测支撑，不是设计想象。

## 1. 核心判断：架构不用重做，缺的是"把三层各自补强"

现状其实已经有很好的内核，只是当时没意识到：

```
App（Express）= 单一事实源：数据 + 权限矩阵 + REST 端点
    ↑ 对话层通过**用户自己的 JWT** 调用这些端点
内置对话助手（轻量 harness，本地模型优先）
    ↑ 同一份工具目录（toolCatalog）按权限裁剪后，经 MCP 暴露
外部 Agent（DSH，付费层）
```

**这个结构最值钱的地方：不管前端是内置对话还是 DSH，最终都落到同一套 REST + 权限矩阵 +
写操作两阶段确认。** 权限只定义一处（`role_permissions` + 路由上的 `requirePermission`），
工具目录自动跟着变（`agentCatalog` 从路由表采集权限），所以不会出现"两条路径权限不一致"。

要补的不是结构，是三层各自的能力缺口。

## 2. 已经验证正确的架构原则

### 2.1 可缓存性是**一等架构约束**（代价 19 倍）

system prompt 里嵌了用户名 → 前缀缓存从第 10 个 token 就分叉 → 后面 8000+ token 的工具表
整段作废。12 个不同用户冷缓存实测：

| | 吞吐 | 缓存命中 |
|---|---|---|
| 用户名在 system prompt | 0.46 req/s | 0% |
| system prompt 静态 | 8.84 req/s | 99% |

**规则**：system prompt 必须按"角色大类 × 静态文本"分叉，**任何用户相关的字节都不许进去**
（名字、日期、ID、偏好…）。用户相关的放当前那条 user 消息。
已有测试守着（`tests/unit/agentPersona.test.js`）。

推论：以后凡是"要不要把 X 放进 system prompt"的讨论，先问"它会不会让前缀分叉"。

### 2.2 一个内核，两个能力边界

工具目录（`toolCatalog`）、权限（`role_permissions`）、写操作确认（`AgentService.confirm`）、
记账（`agent_usage`）——**只有一份实现，内置对话和 MCP 共用**。这条已经在代码里成立，
要守住：新增能力时不要在 MCP 侧再写一套。

### 2.3 模型是可替换资源，不是架构组成

`llm.js` 的 targets 链（本地 → 远端）+ 熔断 + 回落 + 记账，让"用哪个模型"变成配置问题。
实测：本地 17/17 工具选择、0.6s、边际成本 0；不可用时自动回落 DeepSeek，用户无感。

### 2.4 写操作必须两阶段确认（安全边界，不可绕过）

不管请求来自内置对话还是 MCP/DSH，写操作一律先生成待确认动作，用户点确认才落库。
MCP 侧也走同一个 `AgentService.confirm`。**这是把"任意能力"接入系统的前提**：
DSH 再强也只能"申请写"，不能直接写。

### 2.5 成本必须可度量、可封顶，且**记账只存原始 token**

价目表会变（峰谷价、模型换代、本地成本为 0），只存成本数字等于把当时的价目表焊死。
`agent_usage` 只存 `prompt/completion/cache_hit` 原始 token，成本现算。

## 3. 目标架构：一个系统，两条访问路径，三种能力档

```
                          ┌─────────────────────────────┐
                          │  App：数据 + 权限 + REST      │
                          │  role_permissions（唯一权威） │
                          │  写操作两阶段确认              │
                          └───────────┬─────────────────┘
                                      │ 同一份端点 / 同一套权限
        ┌─────────────────────────────┼─────────────────────────────┐
        │                             │                             │
   ┌────▼─────┐               ┌───────▼────────┐            ┌───────▼────────┐
   │ L0 免费   │               │ L1 免费升档     │            │ L2 付费        │
   │ 内置对话  │               │ 内置对话        │            │ 独立 DSH 实例   │
   │ 本地 4B   │               │ 本地优先/API 溢出│            │ dsh-passwords  │
   │ 配额限制  │               │ 日预算封顶       │            │ 多租户+配额+沙箱 │
   └──────────┘               └────────────────┘            └───────┬────────┘
                                                                    │ MCP
                                                          （精简工具集，按需开重工具）
```

**L0/L1 和 L2 的区别不是"模型好坏"，是"能力边界"：**

| | L0/L1（内置对话） | L2（DSH 基座） |
|---|---|---|
| 能做什么 | 系统内固定事务：查/写班级数据（48 个端点） | 任意工作：写文件、跑代码、长多步任务、技能、子代理 |
| 覆盖的需求 | **绝大多数**（"帮我请假/查班费/看作业"） | 长尾（"帮我把这学期班费整理成一份报告"） |
| 成本 | 本地 ≈ 0；溢出到 API 几块钱/千轮 | **¥0.4~1.0/任务**（实测账本） |
| 资源 | 一块 GPU 服务全部人（实测 8.84 req/s） | 每用户独立实例/容器（重） |

**关键认识**：L2 不是"更好的 L0"，是**另一类需求**。所以：
- 不该为了 L2 把 L0 拆掉或合并；
- 也不该用 L0 硬撑 L2 的场景（写报告、处理文件、多步任务它做不了）。

## 4. 还缺什么（按优先级）

### P1 —— MCP 通路验证（最便宜，是 L2 的地基）
- 用 DSH 连上 `/api/mcp`，确认：权限裁剪生效、写操作确认生效、工具调用可用。
- **必须先定的架构决策**：MCP 默认暴露**精简工具集**。
  实测学员 MCP 全量 18781 tok/轮，仅 curated 只有 2889 tok（6.5 倍）——
  而 MCP 的工具 schema **每一轮都要发**。默认精简、重工具按需开。
- 这一步不需要多租户，一个人先跑通即可。

### P2 —— L2 多租户与配额（装 dsh-passwords）
- GPL-3.0；自托管自用不触发分发义务（GPL 无 AGPL 的网络条款），对外交付才需 MIT 路线。
- 它自带配额（每小时 token 上限、每日时长上限）、沙盒三档、审计——正好补上 L2 的成本与安全边界。
- 规模提示：单实例多子用户（轻）适合 3~5 人内测；per-user 容器方案只适合小规模。

### P3 —— L0/L1 的容量与体验（按 `AGENT_CAPACITY_PLAN.md` 的阈值触发）
- 触发条件：回落率 > 10% 或 p95 > 5s 或日轮次 > 2000。
- 手段优先级：溢出路由 → 预热（已做）→ 裁模块工具（**会削能力，最后手段**）。
- **不要**为了并发牺牲能力：修复前缀缓存后余量已有约 11 倍。

## 5. 需要产品决策的点（不是技术问题）

1. **L2 谁付费**：单位/学校出钱，还是个人？这决定 GPL 是否可以接受、以及定价锚点。
2. **L2 的用户边界**：给学员开 `bash`/文件系统吗？（dsh-passwords 有沙盒三档，
   但"给 200 个学生服务器执行权"是安全策略问题，不是技术问题。）
3. **免费层的边界**：`AGENT_DAILY_QUOTA` 现在是 200 轮/人/天，需要重新评估。

## 6. 明确不做的事

- **不把 L0 重建在 DSH 上**：DSH 的 prompt 体量（技能 + 工具）远大于我们精简后的 8.2K，
  200 个免费用户跑在一个 GPU 上不现实，而且给免费用户 bash 是安全雷。
- **不为并发裁掉模块工具**：那是"什么都能干"的逃生通道，且当前余量够（见 §4 P3）。
- **不在两处实现权限**：任何"为了 MCP 方便另写一套工具/权限"的想法都要拒绝。
