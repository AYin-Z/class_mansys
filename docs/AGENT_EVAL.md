# 对话助手工具选择评测（选型与回归门禁）

> 2026-09-12 建立。这是"换模型/改提示词/加工具"之后唯一能给出结论的东西。

## 为什么不能靠通用榜单选型

BFCL 之类的榜单测的是**英文通用函数调用**。我们的场景是：

- 固定的 43~47 个中文工具表（每次请求全量下发，约 6~9K token）
- 中文口语输入（含错别字、简称、方言）
- 需要算日期填参数（"下周一"）
- 有权限边界（学员不该拿到审批类工具）

实测反例：`watt-tool-8B`、`xLAM-2-8b` 这类"工具调用专家"在 BFCL 上分数不低，
但底座是 Llama（中文弱），而 `xLAM-2-8b` 还是 **CC-BY-NC（禁止商用）**；
同尺寸的纯文本新版 `Qwen3-4B-Instruct-2507` 在我们的场景里**不调工具、直接编造数据**
（实测自己编出"总积分 125 分"和"张伟/李娜"这类不存在的记录）——这比不调工具更危险。

**结论：必须用自己的用例做门禁。**

## 怎么跑

```bash
cd backend
# 本地模型（默认门禁线 95%，2 轮）
npm run eval:agent
# 自定义
node tests/eval/run.mjs --base-url http://127.0.0.1:8090/v1 --rounds 2 --min-score 92 \
  --json /tmp/agent-eval.json
# 只跑某几类
node tests/eval/run.mjs --base-url ... --only date-
```

评测器用的是**真实的**目录与提示词（直接 require app 与 persona），不是另写一份"差不多"的，
否则测的不是线上行为。

可用环境变量：`EVAL_NO_THINK=1` 关掉模型的思考模式（Qwen3.5 这类默认开思考，
不关等于用推理模式参加评测）；`EVAL_TEMPERATURE=0` 用确定性采样。

## 用例覆盖（`tests/eval/cases.mjs`）

| 类别 | 例子 | 防的是什么 |
|---|---|---|
| 基础查询 | 我的积分有多少 | 最基本的选择能力 |
| 口语/错别字 | 我明儿个有事儿，帮我请个假 | 只认书面语 |

| 模糊指代 | 查一下张三 | 选错工具 |

## 规模与真实成绩（2026-09-13 扩容后）

从 40 条扩到 **155 条**（33 个意图 × 多种说法 + 28 条特殊用例）。这一步立刻证明了自己的价值：

| 用例数 | 4B 的成绩 |
|---|---|
| 40 条 | 92.5% |
| **155 条** | **85.8%**（温度 0）/ 83.4%（温度 0.2） |

**小评测集一直在骗我：把它当成绩看会高估 7~9 个点。** 原因很直接——
40 条时 37/40 与 39/40 只差 2 条，那是噪声；而且每条意图只有 1 种说法，
碰巧过了就以为会了。换 4~6 种说法后，模型的不稳定性才暴露出来。

失败构成（155 条里的 22 条失败）：

| 类型 | 条数 | 说明 |
|---|---|---|
| **该动手却用文字回答** | **11** | 主要失败模式。同一句话时对时错（"要不要动手"的决策在临界点摇摆） |
| 选错工具 | 4 | 模糊指代（"查一下张三"→classes）；"帮我请个假"→auth |
| 参数取值错 | 1 | "今天下午"被算成明天 |

温度从 0.2 降到 0 能提升约 2.4 个点（83.4% → 85.8%），但主要失败模式依旧。

**这个结论直接改变了微调的判断**：主要失败是**单一的行为契约**（"该动手就动手"），
而不是知识或推理问题——这正是 SFT 最擅长修的东西，而且现在有了可量化的靶子
（85.8% → 95%+）。此前基于 40 条得出的"微调没有收益空间"是被小样本误导的结论。

### 第二轮：只改工具描述（不重训）→ 98.8%

微调后剩下的失败集中在两处**工具混淆**（通知/公告、出勤/请假明细），先试成本最低的路线：
改 `toolCatalog.js` 的描述 + 补一个缺失工具，**不重训**。同时修掉两处**用例自相矛盾**的地方。

| 改动 | 说明 |
|---|---|
| 补 `list_announcements`（GET /api/announcement） | 公告是真实独立功能，目录里原本没有 → 模型只能**编一个不存在的工具名**来答"看看公告" |
| `list_notices` 描述去掉"待办" | 原描述含"待办"，把"有没有待办"（干部审批）吸走了 |
| `pending_leave_approvals` 描述点明"干部审批用、本人请假走 my_leaves" | 原描述"查看全部请假记录"字面撞上"我请的假批下来了吗" |
| `company_attendance` / `company_leave_records` 描述写死分工 | 前者＝人数统计，后者＝人员名单明细 |
| `create_expense` 描述补触发语 | "我要报销35元，买的是扫把"原本被答成文字反问 |
| 用例：`attendance-company` 里的"今天谁请假了"挪到请假明细 | 原期望（出勤概览）与字面（谁在请假）**直接冲突**，模型不可能两边都对 |
| 用例：新增 `announcement-list`、拆出 `expense-create-vague`（allowNoTool） | 缺金额/用途时**追问才是对的**，不该判错 |

**结果（161 条，同一套用例）：**

| 模型 | 通过 | 成绩 |
|---|---|---|
| base（同样修了 schema 与描述） | 147/161 | **91.3%** |
| **+ LoRA** | 159/161 | **98.8%** ✅ |

**净提升 +7.5 个点**，其中"修 schema + 改描述"这两项**不需要重训**就拿到了大部分收益
（LoRA 从 91.7% → 98.8%）。

剩余 2 条（都是模型层面的真混淆，需要更多针对性训练数据，不是描述能修的）：

| 用例 | 错成 | 性质 |
|---|---|---|
| leave-records-company | company_attendance | 出勤概览 vs 请假名单（描述已写死分工，仍偶发） |
| cadre-pending-leave | list_notices | "有没有待办"这类模糊说法 |

### 第一轮的失败构成（供对照，已被上面两轮修掉）

只修 schema、还没动描述时，LoRA 的 6 条失败是：通知/公告混淆、出勤/请假明细混淆、
"我的请假"与"待审批"混淆，以及 `expense-create` 决策摇摆。这正是第二轮改描述的靶子。

## ⚠️ 一个会坑所有模型的 schema 坑（2026-09-14 发现并修复）

`toolCatalog.js` 里 `pathParams`/`query` 原本声明成**纯 `type: 'string'`**。
模型（尤其是小模型）经常把 id 写成裸数字 `{"id": 3}` → **llama.cpp 判定参数不合 schema 后
会内部重试**，把"参数非法"当成新一轮对话喂回模型；模型接着续写这段对话，
一路生成到 `max_tokens` 才停（`finish_reason: length`，参数被解析成 `{"id": "}}</tool_call>` 之类的垃圾）。

实测证据：同一个请求，schema 严格时 `finish=length` + 垃圾参数；把类型放宽成 `['string','number']`
后立刻 `finish=tool_calls` + `{"id": 3}`。这一个坑在旧口径下压掉了 base 约 4 个点、LoRA 约 4.5 个点
（LoRA 91.7% → 96.2%，base 85.8% → 89.7%），而且**表现为"参数不是合法 JSON"，很容易误判成模型的锅**。

修法：`pathParams`/`query` 一律放宽成 `['string','number']`（id 最终拼进 URL，数字与字符串等价）。
**教训**：评测里出现"参数不是合法 JSON"时，先看模型的**原始输出**（`run.mjs` 现在会打印原始参数，
并支持 `EVAL_DUMP_RAW=<文件>` 导出完整请求/响应），不要直接归因于模型能力。

## ⚠️ 评测的一个根本局限（2026-09-21 被真实投诉打脸后补）

**`run.mjs` 的 `ask()` 只发一轮、从不执行工具**——它测的是"第一步有没有选对工具"，
**测不到多步串联**（姓名 → 查人 → 查记录 → 取详情 → 组织回答）。

于是出现了这种尴尬：评测 98.8%，用户真实使用却骂"蠢的令人发指"。复盘的两条真实投诉
（只发一个人名 / 索要数据库内部 ID）**在评测集里根本不存在**——用例是照着"一句话一个意图"
写的，而真实用户会说半个词、会打错名字。

补救（2026-09-21）：

1. **加了 4 条真实投诉回归用例**（`bare-name`、`bare-name-student`、`name-to-detail`、`name-plus-vague`）：
   只给一个人名时**必须至少调一个工具**（先去查），一句都不查就反问即判失败。
2. **新增真实链路探针** `backend/scripts/agent-probe.js`：用线上同一套 prompt/工具目录/执行器跑**完整多步**，
   复现真实投诉用。用法 `node scripts/agent-probe.js "张驭捷" 34`（会写真实会话记录，用完按提示 SQL 清理）。
3. **提示词加了 §1.1b「先自查再问」**（见 AGENT_BEHAVIOR_SPEC.md）——根因是旧判据
   `参数缺失 → 只追问` 被过度套用。

**待办**：把"多步链路"也纳入评测（例如断言最终回复里必须出现查到的东西），现在只断言第一步。
