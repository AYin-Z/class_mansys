# 对话助手容量计划（免费层本地模型 + 付费层 DSH）

> 2026-09-12 制定。所有数字都是本机实测，不是估算；改动前请重测并在本文件更新。

## 0. 结论先行

### 0.1 已修正的错误结论（重要）

**本文件最初写的"免费层并发不是瓶颈、余量 10~20 倍"是错的**，原因是当时的测量方法有缺陷：
我用**同一个 prompt** 反复发请求测吞吐，得到了 24 req/s。但 system prompt 里嵌了用户名，
而**前缀缓存只能从第一个 token 开始匹配**——名字在最前面，于是每个用户的前缀从第 10 来个
token 就分叉，后面 8000 多 token 的工具表完全无法复用。

用 12 个**不同用户**、冷缓存重测：

| 12 并发（12 个不同用户，冷缓存） | 墙钟 | 吞吐 | 前缀缓存命中 |
|---|---|---|---|
| 用户名写在 system prompt 里（原状） | **25.9s** | **0.46 req/s** | **0%** |
| system prompt 静态、身份放进 user 消息（已修） | **1.4s** | **8.84 req/s** | **99%** |

**差 19 倍。** 而峰值需求约 0.8 轮/秒 —— 所以**原状确实不够**，问题真实存在。

修复已上线（2026-09-12）：`persona.buildSystemPrompt()` 改为完全静态，用户身份由
`buildUserContext()` 拼在**当前这条 user 消息**上。生产实测两个不同用户缓存命中
8298/8392（99%）与 8250/8283（99.6%），改造前均为 0%。

**这个不变量有测试守着**（`tests/unit/agentPersona.test.js`：不同用户的 system prompt
必须逐字节相同）——以后谁往 system prompt 里塞用户相关的东西，测试会拦下来。

### 0.2 当前状态

并发已不是瓶颈（8.84 req/s vs 需求 0.8 req/s，余量约 11 倍）。剩下的风险是：

1. 冷启动延迟——"第一次用很卡"本质是**前缀缓存为空**，不是模型慢。
   已用进程内预热解决（每 5 分钟用真实工具表灌一次公共前缀）。
2. 本地服务静默宕机时 **100% 回落 DeepSeek**：360 轮/天 × ¥0.0065 = **¥2.3/天 ≈ 5 周烧完 ¥83 余额**。
   已用 P0 记账 + 回落率告警覆盖。
3. 观测缺失（历史总用量只有 9 条消息）。已用 `agent_usage` 表覆盖。

## 1. 容量实测基线（RTX 5060 Ti 16G，与 Hermes 9B 并存，显存占用 12.8G/16.3G）

### 1.1 每槽上下文需求

每槽上下文 = `n_ctx / n_parallel`（这个 llama.cpp build 的行为），实测：

| 组成 | token |
|---|---|
| 工具表（学员 43 个）+ system prompt（含内联 guide） | **8,284** |
| + 最坏情况 30 条会话历史（`agentService` 的上限） | **11,024** |
| 每槽容量（`-c 65536 --parallel 4` = 16384，减 800 输出预留） | **15,584** |
| **最坏情况余量** | **4,560** |

结论：当前配置下**长对话不会溢出**。但余量只有 4.5K，若将来工具表变大或用户粘贴长文本仍可能吃掉，
所以 P1 要加 token 预算守卫（不是救火，是防回归）。

### 1.2 并发与吞吐实测

**真实（12 个不同用户、冷缓存、完整学员目录）**：

| 场景 | 墙钟 | p50 | 吞吐 | 前缀缓存命中 |
|---|---|---|---|---|
| 用户名在 system prompt（原状） | 25.9s | 21.2s | 0.46 req/s | 0% |
| **静态 system prompt（现行）** | **1.4s** | **0.9s** | **8.84 req/s** | **99%** |

**参考（同一 prompt 反复发，会高估容量——不要用这个数做决策）**：
裁剪到 curated + 12 槽时 24 并发可达 23.7 req/s。

关键规律：**前缀缓存是主导因素，而不命中缓存的根因是 prompt 布局**。
工具表（8000+ tok）对所有同学完全一致，只要 system prompt 是静态的就能整段复用；
一旦最前面出现用户相关的 token，整段作废。**这比并发槽位数重要一个量级**：
调槽位是 4→12（3 倍），修 prompt 布局是 0.46→8.84（19 倍）。

### 1.3 需求侧估算

| 项 | 估算 |
|---|---|
| 全站用户 | 215 |
| 假设日活 30% | 65 人/天 |
| 每人 3 条消息 × 2.5 轮 | ~490 轮/天 |
| 摊到高峰 10 分钟 | **0.8 轮/秒** |
| 修复后容量（实测 8.84 req/s） | **~8.8 轮/秒** |
| 修复前容量（实测 0.46 req/s） | **不够** |

**余量约 11 倍**。最坏情形是 30 人同时按下发送，排队尾巴 1~2 秒，且有流式输出。

## 3. P1 鲁棒性 ✅ 已完成（2026-09-12）

1. **预热** ✅ 已落地：不是独立定时器，而是**后端进程内**每 5 分钟用
   `agentCatalogFor` + `buildSystemPrompt` 的真实内容发一个 `max_tokens=1` 的请求
   （`services/agent/warmup.js`，由 app.js 启动）。放在进程内的原因：预热内容必须与真实请求
   **逐 token 一致**才有用，复用同一份目录和 prompt 才能保证这点。
   `LLM_WARMUP_INTERVAL_MS=0` 可关闭。
2. **历史 token 预算守卫** ✅ 已落地：`services/agent/history.js`，超预算从最旧开始丢，
   至少保留一条（否则模型看不到本轮问题）。默认 `AGENT_HISTORY_TOKEN_BUDGET=4000`，0 = 不限制。
   （另注：system prompt 静态化之后，system + 工具表这段前缀对所有同角色用户都可复用，
   真正逐用户变化的是历史部分，所以这个守卫同时也有缓存收益。）
3. **回落可观测**：`servedBy` 已经返回，接进 P0 的表；4xx 已按请求级错误处理、不计熔断
   （否则长对话几次超限会把本地模型误停 60 秒）。
4. 本地服务健康检查：`serve-local-llm.sh` 已在 systemd 下 `Restart=always`，
   但**进程活着不等于能出结果**，所以要靠 P0 的回落率来发现假死。

## 4. P2 容量（挂在阈值上，数据不到不做）

触发条件（任一）：
- 本地回落率 > 10%，或
- 高峰排队（p95 延迟）> 5s，或
- 真实日轮次 > 2000

手段按性价比排序：

| 手段 | 收益 | 代价 |
|---|---|---|
| ① 队列溢出路由：本地队列深度 > N 时直接走 API | 削峰，成本几块钱 | 要加队列深度观测 |
| ② 裁模块工具（20 个模块工具占 74% 的 prompt） | 槽位 **4 → 12**（同显存实测） | **会削能力**（模块工具是"什么都能干"的逃生通道） |
| ③ 停掉 Hermes 的 9B 腾出 5G | 更多槽位 | 影响别的服务 |
| ④ 加显存 / 换卡 | 线性扩容 | 要花钱 |

**②是最后手段**：实测数据表明当前不需要为并发牺牲能力（余量 3~8 倍）。
如果真要做，用"两段式"保能力：先只用 curated 问一次，模型搞不定再用完整目录重试一次。

## 5. P3 付费层（独立线，用 dsh-passwords）

- 选型依据：`slywalker2006/dsh-passwords` ★52、GPL-3.0、DSH 0.1.5 全版本验证（我们是 rc.1）。
  **自托管自用不触发 GPL 分发义务**（GPL-3.0 没有 AGPL 的网络条款）；将来要交付给别的单位才需要 MIT 路线。
- 它自带的能力正好是我们要的：子用户权限与**配额**（每小时 token 上限、每日时长上限、封禁）、
  **沙盒三档**、工作区白名单、逐会话授权、审计日志、自动 HTTPS。
- 与系统的对接走 **MCP**（已有 `/api/mcp` + api_tokens + 按权限裁剪的工具表）。
- 规模提示：它是**单实例多子用户**（轻），适合先做 3~5 人内测；
  两个 MIT 方案是每用户一个进程/容器（重），只适合小规模付费用户。
- 装之前必须做：审源码、pin commit、验 0.1.5-rc.1 兼容。
