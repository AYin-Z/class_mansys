# 对话助手容量计划（免费层本地模型 + 付费层 DSH）

> 2026-09-12 制定。所有数字都是本机实测，不是估算；改动前请重测并在本文件更新。

## 0. 结论先行

**免费层的并发现在不是瓶颈**，实测余量 10~20 倍。真正会造成损失的是另外三件事：

1. 冷启动延迟（实测 12 并发冷启 **7.9s**，热缓存 **1.0s**）——高峰体验差 8 倍；
2. 本地服务静默宕机时 **100% 回落 DeepSeek**：360 轮/天 × ¥0.0065 = **¥2.3/天 ≈ 5 周烧完 ¥83 余额**；
3. 没有任何观测，回落率和真实峰值全是猜的（历史总用量只有 9 条消息）。

所以本计划的重心是 **P0 观测 → P1 鲁棒性**，容量扩容（P2）挂在明确阈值上，数据不到就不做。

## 1. 容量实测基线（RTX 5060 Ti 16G，与 Hermes 9B 并存，显存占用 12.8G/16.3G）

### 1.1 每槽上下文需求

每槽上下文 = `n_ctx / n_parallel`（这个 llama.cpp build 的行为），实测：

| 组成 | token |
|---|---|
| 工具表（学员 43 个）+ system prompt（含内联 guide） | **8,284** |
| + 最坏情况 30 条会话历史（`agentService` 的上限） | **11,024** |
| 每槽容量（`-c 65536 --parallel 4` = 16384，减 800 输出预留） | **15,584** |
| **最坏情况余量** | **4,560** |

结论：当前配置下**长对话不会溢出**。但余量只有 4.5K，若将来工具表变大或用户粘贴长文本仍可能吃掉，
所以 P1 要加 token 预算守卫（不是救火，是防回归）。

### 1.2 并发与吞吐实测

| 配置 | 每请求 prompt | 1 并发 | 12 并发（冷启） | 24 并发 | 48 并发 |
|---|---|---|---|---|---|
| 学员目录（含 20 个模块工具） | 8,619 tok | — | 不可用（每槽 8K 装不下） | — | — |
| 裁剪到 curated + 12 槽 | 3,364 tok | 0.8s | 7.9s | **1.0s 墙钟 / 23.7 req/s** | **2.0s 墙钟** |

关键规律：**前缀缓存是主导因素**。工具表 + prompt 对所有同学完全一致，
llama.cpp 只算一次；命中后吞吐从 ~1.5 req/s 跳到 ~24 req/s。

### 1.3 需求侧估算

| 项 | 估算 |
|---|---|
| 全站用户 | 215 |
| 假设日活 30% | 65 人/天 |
| 每人 3 条消息 × 2.5 轮 | ~490 轮/天 |
| 摊到高峰 10 分钟 | **0.8 轮/秒** |
| 4 槽容量（每轮 0.6~2s） | **2~6 轮/秒** |

**余量 3~8 倍**（按高峰 10 分钟算）。最坏情形是 30 人同时按下发送：
排队尾巴约 8 秒，但有流式输出，用户立刻能看到字在滚。

## 2. P0 观测（先做，没有它后面全是猜）

- 迁移 024 + `agent_usage` 表：每轮记录 `served_by`（local/remote）、`model`、
  `prompt_tokens`、`completion_tokens`、`cache_hit_tokens`、耗时、是否回落、用户/角色。
- 按天聚合：轮次、回落率、成本估算（价目表可配，含峰谷价——抄 `@linxin666/dsh-usage` 的设计）。
- 余额与回落告警：本地回落率超阈值、或当日估算成本超阈值时报警。

**为什么必须做**：现在无法回答"本地模型到底替你挡了多少、失败了多少、花了多少"。
P2 是否要做，取决于 P0 测出来的回落率——不该凭感觉扩容。

## 3. P1 鲁棒性（半天，零风险，与 P0 并行）

1. **预热定时器**：`class-mansys-llm-warmup.timer` 每 5 分钟发一个最小请求，保持前缀缓存热。
   收益最大、代价最小：高峰延迟 **7.9s → 1.0s**（实测）。
2. **历史 token 预算守卫**：按估算器裁剪会话历史，留 2K 余量。
   当前 30 条上限实测不会溢出（余量 4.5K），这是防回归。
3. **回落可观测**：`servedBy` 已经返回，接进 P0 的表；4xx 已按请求级错误处理、不计熔断
   （否则长对话几次超限会把本地模型误停 60 秒）。
4. 本地服务健康检查：`serve-local-llm.sh` 已在 systemd 下 `Restart=always`，
   但**进程活着不等于能出结果**，所以要靠 P0 的回落率来发现假死。

## 4. P2 容量（挂在阈值上，数据不到不做）

触发条件（任一）：
- 本地回落率 > 10%，或
- 高峰排队（p95 延迟）> 5s，或
- 真实日轮次 > 2000

手段按性价比排序：

| 手段 | 收益 | 代价 |
|---|---|---|
| ① 队列溢出路由：本地队列深度 > N 时直接走 API | 削峰，成本几块钱 | 要加队列深度观测 |
| ② 裁模块工具（20 个模块工具占 74% 的 prompt） | 槽位 **4 → 12**（同显存实测） | **会削能力**（模块工具是"什么都能干"的逃生通道） |
| ③ 停掉 Hermes 的 9B 腾出 5G | 更多槽位 | 影响别的服务 |
| ④ 加显存 / 换卡 | 线性扩容 | 要花钱 |

**②是最后手段**：实测数据表明当前不需要为并发牺牲能力（余量 3~8 倍）。
如果真要做，用"两段式"保能力：先只用 curated 问一次，模型搞不定再用完整目录重试一次。

## 5. P3 付费层（独立线，用 dsh-passwords）

- 选型依据：`slywalker2006/dsh-passwords` ★52、GPL-3.0、DSH 0.1.5 全版本验证（我们是 rc.1）。
  **自托管自用不触发 GPL 分发义务**（GPL-3.0 没有 AGPL 的网络条款）；将来要交付给别的单位才需要 MIT 路线。
- 它自带的能力正好是我们要的：子用户权限与**配额**（每小时 token 上限、每日时长上限、封禁）、
  **沙盒三档**、工作区白名单、逐会话授权、审计日志、自动 HTTPS。
- 与系统的对接走 **MCP**（已有 `/api/mcp` + api_tokens + 按权限裁剪的工具表）。
- 规模提示：它是**单实例多子用户**（轻），适合先做 3~5 人内测；
  两个 MIT 方案是每用户一个进程/容器（重），只适合小规模付费用户。
- 装之前必须做：审源码、pin commit、验 0.1.5-rc.1 兼容。
